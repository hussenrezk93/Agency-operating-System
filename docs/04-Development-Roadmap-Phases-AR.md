# Agency OS — دليل مراحل تطوير النظام (Laravel Development Phases Guide)

خطة تطوير وتنفيذ النظام من Phase 0 إلى Phase 10.

| البند | القيمة |
|---|---|
| الوثيقة | خطة تطوير وتنفيذ النظام |
| النطاق | Phase 0 إلى Phase 10 |
| التقنية | Laravel + PostgreSQL + Blade + Tailwind CSS |
| الهوية | أبيض وبرتقالي — عربي وإنجليزي |

---

## الخريطة العامة للمراحل (00) — من التحليل إلى الاختبار والتسليم

| المرحلة | الاسم | نوع الناتج | أهم نتيجة |
|---|---|---|---|
| 0 | التحليل والتخطيط | لا يوجد كود | خطة تقنية وصلاحيات وWorkflow |
| 0.5 | نموذج الواجهات | واجهة تجريبية | أفضل نقطة مبكرة لعرض الشكل |
| 1 | تأسيس Laravel | واجهة أساسية | Login وLayouts واللغات |
| 2 | قاعدة البيانات | عمل خلفي | Migrations وModels وRelationships |
| 3 | المستخدمون والأقسام | واجهة تشغيلية | Users وDepartments وPermissions |
| 4 | العملاء والمشروعات | واجهة تشغيلية | Projects وClients وWhatsApp |
| 5 | تنفيذ التاسكات | واجهة تشغيلية | Create وAssign وSubmit |
| 6 | المراجعة والتحويل | Demo قوي | Approve وChanges وTransfer وComplete |
| 7 | الإشعارات والبريد | تشغيل خلفي | Deadline Jobs وEmail وQueues |
| 8 | الشات | واجهة تشغيلية | Chats وDigest |
| 9 | التقارير والداشبورد | عرض إداري | KPIs وPerformance |
| 10 | الأمان والاختبارات | جاهزية نهائية | Audit وTests وHardening |

**قاعدة التنفيذ:** لا يتم الانتقال من مرحلة إلى المرحلة التالية إلا بعد مراجعة المخرجات وتشغيل الاختبارات والموافقة الصريحة عليها.

## Phase 0 — التحليل والتخطيط

**هدف المرحلة:** تحويل الـBRD والـERD إلى خطة تقنية واضحة قبل كتابة أي سطر كود.

**المخرجات المتوقعة:**
- Technical Plan معتمد.
- Permissions Matrix.
- State Transition Tables.
- قائمة الأسئلة والتعارضات.
- Roadmap وترتيب تنفيذ واضح.

**ما يتم تنفيذه:**
- قراءة الوثائق كاملة وتحديد نطاق النظام.
- إعداد مصفوفة صلاحيات Admin وManager وTeam Leader وEmployee.
- تحديد حالات التاسك والمشروع والانتقالات المسموحة.
- حصر الجداول والقيود والـJobs والـEvents والـNotifications.
- كشف أي تعارض أو نقص يحتاج قرارًا قبل التنفيذ.

**معيار الموافقة:**
- لا يوجد تعارض غير محلول.
- تم اعتماد الصلاحيات وحالات النظام.
- لا يبدأ أي كود قبل الموافقة.

**الاختبارات والمراجعة:**
- مراجعة كل صلاحية مقابل الـBRD.
- التأكد من أن الـWorkflow لا يسمح بانتقالات غير معتمدة.
- مقارنة قائمة الجداول بالـERD.

> ملاحظة: هذه المرحلة تحليلية فقط، ولا يجب أن تتضمن Migrations أو Models أو Controllers أو Blade files.

## Phase 0.5 — نموذج UX/UI للعرض

مرحلة اختيارية لكنها موصى بها قبل بدء البرمجة.

**هدف المرحلة:** إنشاء نسخة واجهات قابلة للتنقل تساعد صاحب الشركة على اعتماد الشكل وتجربة الاستخدام قبل بناء المنطق الخلفي.

**المخرجات المتوقعة:**
- Prototype قابل للتشغيل والتنقل.
- System Design أبيض وبرتقالي.
- Reusable Blade Components.
- Responsive screens للكمبيوتر والموبايل.

**ما يتم تنفيذه:**
- تصميم Login وDashboards لكل Role.
- تصميم صفحات Users وDepartments وClients وProjects وTasks.
- تصميم Task Timeline وReview وNotifications وChat وReports.
- دعم العربية RTL والإنجليزية LTR.
- استخدام بيانات تجريبية واقعية بدون بناء كل Business Logic.

**معيار الموافقة:**
- اعتماد الهوية البصرية.
- اعتماد ترتيب الشاشات والتنقل.
- تسجيل ملاحظات الإدارة قبل Phase 1.

**الاختبارات والمراجعة:**
- وضوح القوائم والصلاحيات بصريًا.
- سهولة إنشاء Task ومتابعة Timeline.
- عرض عربي وإنجليزي بدون مشاكل اتجاه.
- مراجعة التصميم مع صاحب الشركة.

> ملاحظة: هذه أفضل مرحلة لعرض شكل النظام مبكرًا، لكنها لا تعني أن الوظائف تعمل فعليًا.

## Phase 1 — إعداد Laravel والأساس العام

**هدف المرحلة:** تأسيس مشروع Laravel بطريقة منظمة وتجهيز المصادقة واللغات والتصميم الأساسي.

**المخرجات المتوقعة:**
- مشروع يعمل محليًا.
- Login page وBase Dashboard.
- Localization files.
- UI components الأساسية.
- تعليمات تشغيل واضحة.

**ما يتم تنفيذه:**
- إنشاء Laravel Project وربطه بـPostgreSQL.
- إعداد .env والمنطقة الزمنية Africa/Cairo.
- إعداد Login باستخدام Username وPassword ومنع التسجيل العام.
- إعداد Arabic/English وRTL/LTR.
- إعداد Tailwind CSS والهوية البيضاء والبرتقالية.
- إنشاء Layouts وNavigation الأساسية.
- إعداد Queue وScheduler بصورة أولية.

**معيار الموافقة:**
- Login يعمل.
- التصميم واللغات معتمدة.
- لا توجد أخطاء تشغيل أو Build.

**الاختبارات والمراجعة:**
- تشغيل السيرفر بدون أخطاء.
- اختبار الاتصال بقاعدة البيانات.
- اختبار تسجيل الدخول ومنع Register.
- اختبار تبديل اللغة واتجاه الصفحة.
- اختبار Responsive layout.

## Phase 2 — قاعدة البيانات والموديلات

**هدف المرحلة:** تحويل الـERD إلى قاعدة بيانات حقيقية وموديلات Laravel بعلاقات وقيود صحيحة.

**المخرجات المتوقعة:**
- قاعدة بيانات كاملة.
- Models مترابطة.
- Seed data للحسابات والأقسام التجريبية.
- Migration order موثق.

**ما يتم تنفيذه:**
- إنشاء Migrations بالترتيب الصحيح.
- إنشاء Models وEnums وRelationships.
- إضافة Foreign Keys وUnique Constraints وIndexes.
- إنشاء Factories وSeeders للأدوار والبيانات التجريبية.
- فصل Workflow Status عن Deadline Status.
- منع Hard Delete للكيانات التاريخية حسب الـBRD.

**معيار الموافقة:**
- كل Migrations تعمل من قاعدة فارغة.
- الجداول مطابقة للـERD.
- القيود تمنع البيانات المخالفة.

**الاختبارات والمراجعة:**
- تشغيل `php artisan migrate:fresh --seed`.
- فحص كل Foreign Key وUnique constraint.
- اختبار منع TL نشطين لنفس القسم.
- اختبار منع تكرار القسم في المشروع.
- اختبار العلاقات الرئيسية.

## Phase 3 — المستخدمون والأقسام والصلاحيات

**هدف المرحلة:** بناء الهيكل الإداري للنظام وتطبيق الصلاحيات الفعلية على الخادم.

**المخرجات المتوقعة:**
- صفحات Users وDepartments.
- Policies وMiddleware وGates.
- Temporary TL workflow.
- Routing and output permissions screens.

**ما يتم تنفيذه:**
- إدارة Manager وTL وEmployee.
- تعطيل الحسابات بدل حذفها.
- كلمة مرور مؤقتة وإجبار التغيير عند أول دخول.
- إدارة الأقسام وتعيين TL أساسي.
- إعداد Routing Permissions بين الأقسام.
- إعداد Output Viewing Permissions.
- تنفيذ Temporary TL مع فترة بداية ونهاية وتحويل الصلاحيات.

**معيار الموافقة:**
- الصلاحيات مطبقة Backend وليس UI فقط.
- لا يوجد أكثر من TL فعال للقسم.
- Temporary TL يعمل دون تداخل.

**الاختبارات والمراجعة:**
- محاولة دخول كل Role إلى صفحات غير مسموحة.
- منع TL من إدارة المستخدمين أو الأقسام.
- اختبار Temporary TL أثناء الفترة وبعد انتهائها.
- اختبار تعطيل مستخدم أو قسم مع حفظ التاريخ.

## Phase 4 — العملاء والمشروعات وWhatsApp

**هدف المرحلة:** تنفيذ إدارة العملاء والمشروعات والأقسام المشاركة ودورة حياة رابط جروب WhatsApp.

**المخرجات المتوقعة:**
- Clients module.
- Projects module.
- Project Departments.
- WhatsApp Link Versions.
- Invitation Deliveries log.

**ما يتم تنفيذه:**
- CRUD للعملاء مع التعطيل بدل الحذف.
- إنشاء Project وربطه بعميل واحد.
- إضافة الأقسام المشاركة والروابط العامة.
- حالات Active وCompleted وCancelled.
- منع Tasks جديدة بعد إكمال المشروع.
- إدارة WhatsApp group link وإصداراته.
- إرسال الدعوة للأعضاء المؤهلين وتسجيل التسليم.

**معيار الموافقة:**
- إدارة المشروع تعمل وفق الـBRD.
- تاريخ الروابط والدعوات محفوظ.
- المشروع المكتمل Read Only.

**الاختبارات والمراجعة:**
- منع تكرار القسم في المشروع.
- اختبار صلاحيات TL في اختيار الأقسام.
- تغيير الرابط وإنشاء Version جديد.
- منع تكرار إرسال نفس الإصدار للمستخدم.
- إيقاف الدعوات بعد Completed أو Cancelled.

> ملاحظة: بعد هذه المرحلة يمكن تقديم عرض إداري أول يشمل المستخدمين والأقسام والعملاء والمشروعات.

## Phase 5 — إنشاء التاسكات وتنفيذها

**هدف المرحلة:** بناء بداية رحلة التاسك من الإنشاء وحتى تسليم الموظف للمراجعة إلى Team Leader.

**المخرجات المتوقعة:**
- Task creation form.
- TL assignment screen.
- Employee task screen.
- Outputs and comments.
- Workflow timeline الأساسية.

**ما يتم تنفيذه:**
- إنشاء Task مستقلة أو داخل Project.
- توليد Task Number تلقائي.
- اختيار First Department والأولوية والروابط والملاحظات.
- استلام TL للتاسك وتعيين موظف واحد أو نفسه.
- تحديد Start Date وEnd Date الساعة 11:59 PM.
- تسجيل First View للموظف.
- إضافة Output Links ومنع Submit بدون Output.
- حفظ Task Route وTask Step history.

**معيار الموافقة:**
- رحلة Create → Assign → Open → Add Output → Submit تعمل.
- كل التواريخ والأشخاص محفوظون في History.

**الاختبارات والمراجعة:**
- اختبار وصول التاسك إلى TL الصحيح.
- منع تعيين أكثر من موظف لنفس Step.
- تسجيل أول فتح مرة واحدة.
- منع Submit بدون Output.
- منع الموظف من رؤية Tasks غير مسندة له.

## Phase 6 — المراجعة والتحويل والإكمال

**هدف المرحلة:** إكمال Workflow التاسك بكل قرارات المراجعة والانتقال والتوقف والإلغاء.

**المخرجات المتوقعة:**
- Review screens.
- Transition services.
- Complete task timeline.
- Hold/Resume/Cancel/Redirect actions.

**ما يتم تنفيذه:**
- Approve وChanges Request مع سبب إجباري.
- إرجاع التعديلات لنفس الموظف.
- Send to Next Department من الأقسام المسموحة.
- Finish Task بعد Approval فقط.
- Self assigned TL review بواسطة Manager.
- Hold On وResume وتمديد الموعد.
- Redirect بواسطة Manager مع سبب.
- Cancel Task ومنع Reopen.

**معيار الموافقة:**
- رحلة Task كاملة تعمل من الإنشاء للإكمال.
- كل Transition مصرح ومسجل.
- لا توجد طرق لتجاوز Workflow.

**الاختبارات والمراجعة:**
- منع In Progress → Completed مباشرة.
- اختبار Changes Request ثم إعادة التسليم.
- اختبار التحويل لقسم غير مسموح.
- اختبار TL لا يعتمد عمله الشخصي.
- اختبار Read Only بعد Completed أو Cancelled.

> ملاحظة: هذه أفضل نقطة لعرض Demo تشغيلي لصاحب الشركة لأن المسار الأساسي للنظام أصبح يعمل بالكامل.

## Phase 7 — الإشعارات والبريد والمهام الخلفية

**هدف المرحلة:** تنفيذ إشعارات النظام والبريد والـQueues والـScheduler بدون التأثير على سرعة أو استقرار الـWorkflow.

**المخرجات المتوقعة:**
- Notification center.
- Email templates.
- Queue jobs and scheduled commands.
- Delivery logs and retry fields.

**ما يتم تنفيذه:**
- In-App Notifications لكل أحداث التاسك.
- Email Verification بصلاحية 24 ساعة.
- إرسال البريد عبر Queue.
- تسجيل Queued وSent وFailed وBounced.
- Retry logic عند الفشل.
- تنبيه قبل Deadline بـ24 ساعة وعند Overdue.
- Chat Digest كل ساعتين عند وجود رسائل جديدة.
- Temporary TL start/end scheduled jobs.

**معيار الموافقة:**
- الإشعارات داخل النظام فورية.
- الإيميلات تعمل من Queue.
- الفشل مسجل ولا يوقف العمليات.

**الاختبارات والمراجعة:**
- تشغيل `queue:work` و`schedule:work`.
- اختبار بريد غير Verified.
- اختبار فشل البريد بدون تعطيل Workflow.
- اختبار عدم تكرار Reminder.
- اختبار Digest لا يُرسل عند عدم وجود رسائل.

## Phase 8 — نظام الشات

**هدف المرحلة:** توفير تواصل داخلي منظم وفق أنواع المحادثات والصلاحيات المحددة.

**المخرجات المتوقعة:**
- Conversations and participants.
- Chat interface.
- Message deletion flow.
- Digest integration.

**ما يتم تنفيذه:**
- Employee–TL private chat.
- Department group chat.
- Private chat بين TLs.
- All TLs group.
- Manager with TLs group.
- دعم النص والروابط فقط.
- منع Edit والسماح للمرسل بالحذف.
- حذف محتوى الرسالة للجميع وتسجيل الحدث فقط في Audit Log.

**معيار الموافقة:**
- كل نوع شات يعمل بالصلاحيات الصحيحة.
- الرسالة المحذوفة لا يبقى محتواها.

**الاختبارات والمراجعة:**
- منع مستخدم غير مشارك من قراءة المحادثة.
- منع حذف رسالة شخص آخر.
- التحقق من إزالة body بعد الحذف.
- اختبار حماية النص والروابط من XSS.

## Phase 9 — الداشبورد والتقارير والأداء

**هدف المرحلة:** تحويل بيانات النظام إلى لوحات متابعة وتقارير تساعد الموظفين والقيادات على اتخاذ القرار.

**المخرجات المتوقعة:**
- Role-based dashboards.
- Performance reports.
- Charts and KPI cards.
- Export-ready report views.

**ما يتم تنفيذه:**
- Employee Dashboard للمهام والأداء الشخصي.
- TL Dashboard للتعيينات والمراجعات وأداء القسم.
- Manager Dashboard للمشروعات والأقسام والتأخيرات.
- حساب Employee Monthly Score.
- حساب Department Overdue Rate.
- تقارير Tasks وProjects وEmployees وTLs.
- Filters حسب الشهر والقسم والحالة.

**معيار الموافقة:**
- النتائج الحسابية صحيحة.
- كل Role يرى تقاريره فقط.
- الواجهة صالحة للعرض الإداري.

**الاختبارات والمراجعة:**
- حساب الأداء يدويًا ومقارنته بالنظام.
- استبعاد Cancelled وOn Hold حسب القواعد.
- إظهار N/A بدل 0 عند عدم وجود مراحل مستحقة.
- اختبار الفلاتر وصلاحيات التقارير.

> ملاحظة: بعد هذه المرحلة يكون النظام شبه نهائي ويمكن تقديم عرض إدارة شامل بالـKPIs والتقارير.

## Phase 10 — الأمان والاختبارات والتسليم

**هدف المرحلة:** مراجعة النظام بالكامل وتأمينه وإثبات جاهزيته للاستخدام والإطلاق.

**المخرجات المتوقعة:**
- Audit Log مكتمل.
- Automated test suite.
- Security checklist.
- Deployment documentation.
- Final acceptance report.

**ما يتم تنفيذه:**
- إكمال Audit Log لكل الأحداث الحساسة.
- اختبارات Policies ومنع IDOR وMass Assignment.
- Rate Limiting وCSRF وSession Security.
- Feature وUnit وWorkflow وQueue tests.
- اختبار Mobile وTablet وDesktop.
- مراجعة RTL/LTR.
- مقارنة نهائية مع الـBRD والـERD.
- إعداد Deployment وBackup وOperational Guide.

**معيار الموافقة:**
- كل الاختبارات ناجحة.
- لا توجد ثغرات حرجة معروفة.
- تمت الموافقة النهائية مقابل الـBRD والـERD.

**الاختبارات والمراجعة:**
- تشغيل `php artisan test`.
- اختبارات مستخدم غير مصرح له لكل عملية حساسة.
- اختبار الروابط والمدخلات ضد XSS وIDOR.
- اختبار النسخ الاحتياطي والاستعادة.
- اختبار النشر على بيئة مماثلة للإنتاج.

## متى يمكن عرض النظام لصاحب الشركة؟

| نقطة العرض | الوصف | تنبيه |
|---|---|---|
| بعد Phase 0.5 | عرض بصري مبكر — عرض الشاشات ببيانات تجريبية لاعتماد التصميم وتجربة الاستخدام | واجهة فقط وليست وظائف مكتملة |
| بعد Phase 4 | عرض إداري أول — Login والمستخدمون والأقسام والعملاء والمشروعات وWhatsApp | مناسب لمراجعة الهيكل الإداري |
| بعد Phase 6 | أفضل Demo تشغيلي — رحلة Task كاملة من الإنشاء حتى المراجعة والتحويل والإكمال | أفضل نقطة لاعتماد منطق النظام |
| بعد Phase 9 | عرض شبه نهائي — الداشبورد والتقارير والأداء بجانب الوظائف الأساسية | مراجعة الإدارة قبل الاختبارات النهائية |

**التوصية:** اعرض نموذج الواجهات بعد Phase 0.5 للموافقة على الشكل، ثم اعرض Demo تشغيلي كامل بعد Phase 6 للموافقة على مسار التاسك.
